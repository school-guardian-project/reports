2. Verificación E2E en Entorno Real

Se verificó la funcionalidad contra el entorno desplegado: Web en https://guardian-escolar.vercel.app y API en https://school-guardian.duckdns.org (Kong OSS :443, con Caddy delante), usando las credenciales proporcionadas. A continuación los flujos recorridos:

FlujoCredencialesResultadoDetalle observado
Acceso a la web—OK HTTP 200. SPA Angular cargada correctamente en Vercel.
LoginAdmin: admin2@school-guardian.com / 99000000005 OK HTTP 200. Se emite accessToken (JWT RS256, rol Admin, 14 permisos), refreshToken en cookie HttpOnly/Secure/SameSite=None, expiración 60 min (access) / 7 días (refresh). Rate limiting activo en Kong (20 req/min, 200 req/hora por IP en login).
LoginSuperadmin: sch00l.guardi4n@gmail.com / Guardian24 FALLA HTTP 401 INVALID_CREDENTIALS. El superadmin no puede iniciar sesión con las credenciales proporcionadas en el entorno de producción.
GET /api/v1/auth/profileToken Admin OK HTTP 200. Perfil del admin retornado correctamente. Rate limiting por header Authorization (300 req/min).
GET /school-management/schoolsToken Admin FALLA HTTP 404. El endpoint de escuelas no responde (servicio alcanzable: server Kestrel, pero ruta no encontrada).
GET /fleet/busesToken Admin FALLA HTTP 404. El endpoint de buses no responde.
GET /route/routesToken Admin FALLA HTTP 404. El endpoint de rutas no responde.
GET /notification/alertsToken Admin FALLA HTTP 404. El endpoint de alertas no responde.
Interpretación: ms-iam y Kong funcionan correctamente en producción (login, JWT, refresh, profile). Sin embargo, los servicios .NET (school-management, fleet, route, notification) están alcanzables a través de Kong pero sus endpoints devuelven 404, lo que indica problemas de enrutamiento/despliegue en producción o rutas no mapeadas en Kong. El superadmin no puede autenticarse.

3. Hallazgos Detallados por Servicio

3.1 API Gateway (Kong)

ms-api-gateway — kong.yml, plugin custom sg-jwt, docker-compose del gateway.
GW-01 · CORS con orígenes de túnel efímero y credenciales habilitadas
Severidad: AltoCategoría: Seguridad / CORSArchivo: kong.yml:66-74

Descripción

La configuración CORS común incluye orígenes públicos/ephémeros de túnel (ngrok-free.dev, trycloudflare.com, school-guardian.duckdns.org, scarecrow-backspin-vanish.ngrok-free.dev, incurred-stroke-town-fares.trycloudflare.com) e IPs privadas (192.168.100.211:8081/8082), con credentials: true. Un atacante podría reclamar uno de estos dominios efímeros y realizar peticiones autenticadas con credenciales de usuarios reales.

Recomendación: Eliminar orígenes de túnel e IPs privadas; mantener solo dominios propios y restringir credenciales a orígenes de confianza.
GW-02 · Sin límite de cuerpo de petición ni timeouts
Severidad: AltoCategoría: Resiliencia / DoSArchivo: kong.yml (servicios y plugins)

Descripción

Kong no define client_max_body_size por ruta ni timeouts de connect/read/send. Un atacante puede enviar cuerpos grandes para agotar memoria (DoS) o mantener conexiones abiertas.

Recomendación: Añadir límite de cuerpo (p. ej. 1 MB) y timeouts de respuesta en cada ruta/servicio upstream.
GW-03 · Rate limiting insuficiente y KONG_TRUSTED_IPS 0.0.0.0/0
Severidad: AltoCategoría: Seguridad / Rate limitingArchivo: kong.yml:58-62, 97-102; docker-compose.yml:20-26

Descripción

El rate limiting general usa política local (no funciona en clúster) y se limita por header Authorization; el login limita por IP (20/min, 200/h). No hay rate limit dedicado a /refresh, /logout, /health ni a /api/v1/password*. Además, KONG_TRUSTED_IPS: 0.0.0.0/0 permite suplantar IP mediante X-Forwarded-For.

Recomendación: Añadir rate limit por IP en /refresh, /logout, /health, /api/v1/password*; usar política cluster si hay varios nodos; restringir KONG_TRUSTED_IPS al proxy de confianza (Caddy).
GW-04 · Sin consulta de deny-list de tokens revocados
Severidad: MedioCategoría: Seguridad / SesionesArchivo: kong/plugins/sg-jwt/handler.lua

Descripción

El plugin sg-jwt valida la firma RS256 del JWT contra JWKS de ms-iam pero no consulta una deny-list, por lo que un token robado permanece válido hasta su expiración natural incluso tras logout o revocación.

Recomendación: Documentar el TTL máximo aceptado o añadir consulta corta-caché a la deny-list persistente de IAM antes de aceptar el token.
GW-05 · strip_path inconsistente (false en iam/forgot/gps, true en el resto)
Severidad: MedioCategoría: ConfiguraciónArchivo: kong.yml:39, 54, 206, 243 vs 117, 135, 155, 173, 192

Descripción

ms-iam, ms-forgot-information y ms-gps reciben el prefijo completo (strip_path: false); el resto lo descarta. Acopla los upstreams al prefijo del gateway y dificulta diagnósticos de 404 y cambios de versionado.

Recomendación: Estandarizar strip_path o documentar explícitamente el contrato prefix-aware de iam/forgot/gps.
GW-06 · public_paths por prefijo en sg-jwt
Severidad: MedioCategoría: Seguridad / AutenticaciónArchivo: kong/plugins/sg-jwt/handler.lua:79-86; kong.yml:18-24

Descripción

La comparación de rutas públicas usa coincidencia por prefijo. El comentario de kong.yml advierte que añadir un bare /api/v1/auth haría públicos /profile y /terms/*. Fragilidad de diseño para futuras adiciones.

Recomendación: Mantener public_paths como rutas exactas y validar que cualquier futura adición no exponga subrutas no intencionadas.
GW-07 · Health check /health inexistente en Kong vs documentación
Severidad: BajoCategoría: DocumentaciónArchivo: kong.yml vs docs/10-devops/local-setup.md

Descripción

El runbook y local-setup documentan curl localhost:8000/health, pero kong.yml no define ruta /health; el health es responsabilidad de cada servicio backend, no del gateway.

Recomendación: Añadir ruta /health en Kong o corregir la documentación para que apunte a cada servicio.
GW-08 · X-User-Role inyectado condicionalmente
Severidad: BajoCategoría: Funcionalidad / Contexto de usuarioArchivo: kong/plugins/sg-jwt/handler.lua:185-191

Descripción

X-User-Role solo se inyecta si el token trae roleId; si falta, el upstream recibe X-User-Id sin rol. docs promete X-User-Id y X-User-Role siempre.

Recomendación: Inyectar un rol por defecto (vacío o "unauthenticated") cuando falte, o documentar que X-User-Role es opcional.

3.2 ms-iam (Autenticación e IAM)

Spring Boot/Java — LoginService, TokenProvider, RefreshTokenService, LogoutService, controladores /api/v1/auth/*.
IAM-01 · Ausencia de rate limiting y bloqueo de cuenta por intentos fallidos
Severidad: CríticoCategoría: Seguridad / AutenticaciónArchivo: LoginService.java; Seguridad: DIAGNOSTICO_ERROR_ATTEMPTCOUNT.md (no existe)

Descripción

LoginService no implementa conteo de intentos fallidos por email/IP ni bloqueo temporal de cuenta. Está expuesto a credential stuffing y fuerza bruta sin freno. El documento DIAGNOSTICO_ERROR_ATTEMPTCOUNT.md referenciado no existe en el repositorio.

Recomendación: Implementar rate limiting por email e IP en LoginService con bloqueo temporal tras N fallos (p. ej. 5 fallos → bloqueo 15 min) y contadores en Redis/BD.
IAM-02 · Logout no revoca el refresh token ni cierra la sesión
Severidad: AltoCategoría: Seguridad / SesionesArchivo: LogoutService.java

Descripción

LogoutService no revoca el refresh token persistido ni finaliza la SessionProfileEntity. Un refresh token robado sigue siendo válido hasta su expiración (7 días) a pesar de que el usuario cierre sesión.

Recomendación: En logout, marcar el refresh token como revocado y la sesión como terminada; invalidar todas las sesiones del perfil si se solicita "cerrar en todos los dispositivos".
IAM-03 · Deny-list de tokens en memoria (no compartida ni persistente)
Severidad: AltoCategoría: Seguridad / TokensArchivo: InMemoryTokenDenyList

Descripción

La denylist de tokens revocados vive en memoria de la instancia. En entorno con varios pods/replicas, un token revocado en una instancia sigue siendo válido en las demás.

Recomendación: Sustituir por denylist persistente/compartida (Redis) consultada por todas las instancias antes de aceptar un refresh.
IAM-04 · RsaKeyProvider genera claves RSA efímeras si faltan JWT_PRIVATE_KEY/JWT_PUBLIC_KEY
Severidad: AltoCategoría: Seguridad / Consistencia-docsArchivo: RsaKeyProvider.java:112-120; README.md:34-37

Descripción

Si faltan las variables de entorno JWT, la app genera un par de claves RSA efímero en arranque en lugar de fallar. Todos los JWT emitidos se invalidan en cada reinicio y el kid del JWKS no es estable.

Recomendación: Hacer que la aplicación falle al arrancar si faltan JWT_PRIVATE_KEY y JWT_PUBLIC_KEY; mantener claves estables entre reinicios.
IAM-05 · Credenciales reales en texto plano en .env (sa de SQL Server, clave privada RSA, API key interna)
Severidad: AltoCategoría: Seguridad / SecretosArchivo: ms-iam/.env:5, .env:19-20

Descripción

.env contiene MSSQL_SA_PASSWORD=[REDACTED], la clave privada RSA PKCS#8 completa de JWT y APP_INTERNAL_API_KEY. Aunque .env está en .gitignore, existe en disco con valores reales y .env.example expone la estructura completa.

Recomendación: Mover secretos a un gestor (AWS Secrets Manager / variables de entorno del orquestador), rotar la clave privada JWT y la contraseña de sa expuestas, y dejar .env.example con placeholders vacíos.
IAM-06 · Enumeración de usuarios vía códigos de estado distintos
Severidad: MedioCategoría: Seguridad / AutenticaciónArchivo: LoginService.java:39-49, 51-54

Descripción

El login distingue "correo no existe", "contraseña inválida" y "cuenta inactiva" en logs y excepciones. Aunque los mensajes al cliente son genéricos ("Invalid credentials"), el comportamiento diferencial permite enumerar emails activos.

Recomendación: Unificar todas las fallas de autenticación bajo un único mensaje y código 401 genérico; evitar diferenciar en logs que puedan filtrarse.
IAM-07 · Dos @RestControllerAdvice con mapeo inconsistente de excepciones
Severidad: MedioCategoría: Buenas prácticas / Consistencia-docsArchivo: GlobalExceptionHandler.java; AuthExceptionHandler.java

Descripción

Dos clases @RestControllerAdvice manejan InvalidCredentialsException y AccountInactiveException sin @Order. GlobalExceptionHandler mapea cuenta inactiva a 403, AuthExceptionHandler a 401. Comportamiento no determinista según la instancia que procese la petición.

Recomendación: Consolidar en un único @RestControllerAdvice con @Order explícito; mapear todas las fallas de auth a 401 genérico y documentar el contrato de errores en OpenAPI/Scalar.
IAM-08 · Sin límite de sesiones concurrentes ni revocación global por perfil
Severidad: MedioCategoría: Seguridad / SesionesArchivo: RefreshTokenService.java:77-83; AuthenticationRepositoryImpl.java:126-131

Descripción

No hay límite de refresh tokens activos por usuario ni invalidación de todas las sesiones al cambiar contraseña. Un atacante con refresh token robado mantiene sesiones paralelas indefinidamente (cada refresh extiende DateEnd).

Recomendación: Añadir límite de refresh tokens activos por sesión/usuario y operación de revocación global de sesiones de un perfil (tras cambio de contraseña o compromiso).
IAM-09 · Refresh token sin jti obligatorio vinculado a la sesión
Severidad: BajoCategoría: Buenas prácticas / TokensArchivo: JwtTokenProvider.java:59; RefreshTokenService.java:33-46

Descripción

El jti del access token es opcional y delegado al llamador (UUID aleatorio si no viene). No hay jti obligatorio único vinculado a la entidad persistida para revocación granular.

Recomendación: Generar siempre jti UUID único en ambos tokens, almacenarlo vinculado a la sesión y consultar denylist en validación de refresh.
IAM-10 · Health check público sin rate limiting propio
Severidad: BajoCategoría: Buenas prácticasArchivo: AuthController.java:36-40; SecurityConfig.java:28

Descripción

GET /api/v1/auth/health está bajo permitAll() y expuesto públicamente sin rate limiting propio; vector de sondeo o DoS ligero.

Recomendación: Mantener público pero aplicar rate limiting por IP en Kong específicamente para este endpoint.

3.3 ms-user-management

.NET/C# — controladores PersonsController, ProfileLookupController; repositorios PersonRepository; DTOs de cambio de estado.
UM-01 · Contraseña de BD en texto plano en .env (compartida por 3 servicios)
Severidad: CríticoCategoría: Seguridad / SecretosArchivo: ms-user-management/.env:1

Descripción

Cadena de conexión con Password=[REDACTED] para el usuario sgadmin. El mismo secreto se repite en ms-school-management/.env y ms-fleet/.env (un solo sa para los tres servicios). Aunque .env está en .gitignore, existe en disco con credenciales reales.

Recomendación: Mover a gestor de secretos, rotar [REDACTED] inmediatamente y usar credenciales distintas por servicio.
UM-02 · PATCH /persons/{id}/status sin acotar a tenant y DTO sin validación
Severidad: AltoCategoría: Seguridad / Validación de entradaArchivo: PersonsController.cs:26-33; ChangePersonStatusRequestDto

Descripción

El endpoint solo lleva [RequirePermission(UsersManage)] y no acota el id al colegio/sede del llamante. El DTO Status es string sin [Required] ni enum; la validación ocurre solo en el caso de uso. Riesgo de cambiar estado de personas de otros colegios si el guard falla.

Recomendación: Añadir [Required] y validación de enum al DTO, y filtro de tenant explícito en el controlador además del guard de aplicación.
UM-03 · Consultas sin paginación en PersonRepository
Severidad: MedioCategoría: Rendimiento / Buenas prácticasArchivo: PersonRepository.cs:37-54

Descripción

GetAllAsync() ejecuta .ToListAsync() sin .Take() ni filtro de tenant en el repositorio. Permite volcado ilimitado de personas (DoS/memoria) si se expone.

Recomendación: Paginar GetAllAsync (page size por defecto + Take) y aplicar filtro de tenant en el repositorio, no solo en el guard.
UM-04 · Excepciones genéricas devuelven 500 en lugar de 404
Severidad: MedioCategoría: Manejo de errores / ConsistenciaArchivo: PersonRepository.cs:49, 66; ApiErrors.cs

Descripción

Se lanzan new Exception("Person not found") en lugar de excepciones de dominio. ApiErrors no las mapea, así que devuelven 500 rompiendo el contrato de ProblemDetails consistentes.

Recomendación: Sustituir por PersonNotFoundException para que ApiErrors devuelva 404.
UM-05 · Detail=ex.Message expone detalles internos
Severidad: BajoCategoría: SeguridadArchivo: ApiErrors.cs:69

Descripción

El cuerpo ProblemDetails expone ex.Message con detalles técnicos internos al cliente.

Recomendación: Ocultar detalles internos en respuestas de error; usar mensajes genéricos para el cliente y loguear el detalle en el servidor.

3.4 ms-school-management

.NET/C# — REST (puerto 8080) y gRPC interno (5001); SchoolController, CampusController; TenantProvider/JwtTenantProvider.
SM-01 · IDOR: listado de sedes por colegio sin filtro de tenant
Severidad: CríticoCategoría: Seguridad / IDORArchivo: SchoolController.cs:125-130; ListCampusesBySchoolService.cs:17-21

Descripción

GET /api/v1/schools/{id}/campuses no tiene atributo de autorización ni verifica que el colegio pertenezca al tenant del llamante. Cualquier usuario autenticado puede listar sedes de cualquier colegio adivinando el GUID.

Recomendación: Aplicar ISchoolAccessPolicy.EnsureCanAccessAsync(schoolId) antes de consultar sedes.
SM-02 · Dos ITenantProvider con lógica inconsistente (admin sin schoolId ve todos los colegios)
Severidad: AltoCategoría: Seguridad / Consistencia-docsArchivo: TenantProvider.cs; JwtTenantProvider.cs; ServiceCollectionExtensions.cs:29

Descripción

TenantProvider filtra si RoleId != null && != 5; JwtTenantProvider para rol Admin exige SchoolId.HasValue, sino ShouldFilter=false → sin filtro, acceso total. Un admin sin claim schoolId vería todos los colegios.

Recomendación: Unificar ITenantProvider en una única implementación con reglas documentadas (Admin ⇒ schoolId; Student/Driver/Parent ⇒ campusId; SuperAdmin ⇒ sin filtro; fail-closed si no se resuelve).
SM-03 · Confianza ciega en cabeceras X-User-* del gateway
Severidad: AltoCategoría: Seguridad / AutenticaciónArchivo: GatewayAuthenticationHandler.cs:38-67

Descripción

El esquema "Gateway" construye la identidad a partir de X-User-Id, X-Campus-Id, X-School-Id confiando en que Kong las inyecte y borre las entrantes. Si Kong falla o se accede al servicio directamente, se puede suplantar cualquier identidad (schoolId/campusId).

Recomendación: Validar en middleware que las peticiones REST provengan de Kong (IP de confianza o cabecera firmada) antes de aceptar X-User-*.
SM-04 · Sin migraciones EF Core ni definición de índices
Severidad: MedioCategoría: Rendimiento / PersistenciaArchivo: (infraestructura) — no se encontró carpeta Migrations

Descripción

No se encontró carpeta Migrations ni definición de índices de base de datos en el servicio (idem en los otros .NET). Riesgo de missing indexes y sin estrategia controlada de evolución del esquema.

Recomendación: Añadir migraciones EF Core e índices al menos sobre columnas de filtro de tenant (SchoolId, CampusId, Status).
SM-05 · Atributos de autorización duplicados en los 3 servicios .NET
Severidad: BajoCategoría: Buenas prácticas / ConsistenciaArchivo: RequirePermissionAttribute.cs; RequireRoleAttribute.cs (x3 servicios)

Descripción

RequirePermissionAttribute y RequireRoleAttribute se duplican textualmente en ms-user-management, ms-school-management y ms-fleet, dificultando el mantenimiento consistente de la política de autorización.

Recomendación: Extraer a una librería compartida o paquete NuGet interno para evitar duplicación y drift de políticas.

3.5 ms-fleet

.NET/C# — BusController, GpsDeviceController; IamGrpcClient/FleetGrpcClient con InternalApiKeyInterceptor; BusRepository.
FL-01 · Secretos hardcodeados en .env (BD, Iam__ApiKey, Fleet__ApiKey compartidos)
Severidad: CríticoCategoría: Seguridad / SecretosArchivo: ms-fleet/.env:1, 7, 10

Descripción

Password=[REDACTED] en texto plano; además Iam__ApiKey y Fleet__ApiKey comparten el mismo valor base64. Un solo secreto para autenticación inter-servicio y acceso a BD, expuesto en archivo de configuración.

Recomendación: Mover Iam__ApiKey, Fleet__ApiKey y contraseña de BD a gestor de secretos; usar valores distintos por servicio y rotar la clave actual.
FL-02 · GET /buses/assigned/{profileId} sin atributo de autorización (IDOR)
Severidad: AltoCategoría: Seguridad / IDORArchivo: BusController.cs:137-149

Descripción

El endpoint no tiene [RequirePermission] ni [RequireRole]; depende únicamente del decorador DI AuthorizedGetBusAssignedToDriverService. Si el registro DI cambia o se consume la consulta cruda, se puede consultar el bus asignado de cualquier perfil.

Recomendación: Añadir [RequirePermission(BusesRead)] o [BusesManage] explícitamente en GetAssignedToDriver.
FL-03 · GET /api/gps-devices lista todos los dispositivos sin filtro de tenant (oversharing)
Severidad: AltoCategoría: Seguridad / IDOR (oversharing)Archivo: GpsDeviceController.cs:24-30

Descripción

Exige solo BusesManage y lista todos los dispositivos GPS sin filtro por campus/colegio del tenant. Un usuario ve dispositivos de otros colegios.

Recomendación: Filtrar GpsDeviceController.List por las sedes visibles del tenant.
FL-04 · GetAllAsync sin .Take() — resultado ilimitado (DoS)
Severidad: MedioCategoría: Rendimiento / PersistenciaArchivo: BusRepository.cs:25-34

Descripción

GetAllAsync(campusIds, ...) devuelve .ToListAsync(ct) sin .Take(). Usado por ListBasic y Search; con flota grande agota memoria y CPU.

Recomendación: Paginar GetAllAsync y endpoints de listado; buscar con filtros en SQL.
FL-05 · Nombre de tabla erróneo DriverAssignemts (falta la 'n')
Severidad: MedioCategoría: Buenas prácticas / CorrectividadArchivo: FleetContext.cs:28

Descripción

DriverAssignemts es un error tipográfico. Si la tabla real es DriverAssignments, las consultas de asignaciones fallan en runtime. GpsDevice está ExcludeFromMigrations() pero se consulta directamente.

Recomendación: Corregir DriverAssignemts → DriverAssignments y revisar que todas las tablas consultadas estén en las migraciones.
FL-06 · Patrón N+1 en ListBusesBasicService
Severidad: MedioCategoría: RendimientoArchivo: ListBusesBasicService.cs:42-59

Descripción

Por cada bus consulta GetActiveByBusIdAsync, GetDriverNameAsync (gRPC a ms-iam) y GetModelNamesAsync (caché parcial). N+1 de llamadas gRPC/BD por bus listado.

Recomendación: Eager-load / batch de datos relacionados y completar caché de modelos para eliminar el N+1.
FL-07 · Search materializa lista completa en memoria y filtra después en LINQ
Severidad: MedioCategoría: Rendimiento / PersistenciaArchivo: SearchBusesService.cs:21-34; BusRepository.cs:25-34

Descripción

Search ejecuta GetAllAsync() completo y filtra en memoria con .Where(...) sin paginación ni filtro en SQL.

Recomendación: Aplicar filtros y paginación en la consulta SQL (EF Core), no en memoria.

3.6 ms-route

.NET/C# — controladores Route/Stop/City/Trip/RouteAssignment; repositorios; gRPC RouteGrpcService.
R-01 · Repositorios sin paginación consistente
Severidad: MedioCategoría: RendimientoArchivo: RouteRepositoryImpl.cs y demás repositorios

Descripción

Los repositorios de route no aplican paginación consistente en listados (GetAll sin Take), exponiendo volcado de datos en flotas grandes.

R-02 · Filtro de tenant no aplicado en todos los repositorios de lectura

4. Conclusión y Veredicto

El proyecto School Guardian presenta una arquitectura de microservicios bien estructurada (Kong como gateway, JWT RS256 con JWKS, separación hexagonal en los servicios .NET, rotación de refresh tokens, gRPC para comunicación interna, Kafka para notificaciones), pero con debilidades críticas de seguridad y operación que impiden considerar el sistema listo para producción sin remediación.

Hallazgos más críticos: (1) secretos reales commiteados en sg-ms-forgot-information (.env y docker-compose: contraseña SMTP, sa de RDS, API keys Twilio, OTP pepper) y Firebase Admin private_key en el frontend mobile; (2) ausencia de rate limiting y bloqueo de cuenta en ms-iam (fuerza bruta/credential stuffing); (3) sg-ms-gps referenciado en Kong/arquitectura pero ausente del despliegue; (4) IDOR en listado de sedes de ms-school-management y endpoints sin autorización en ms-fleet; (5) CORS con orígenes de túnel efímero y KONG_TRUSTED_IPS 0.0.0.0/0.

Veredicto general: NO LISTO PARA PRODUCCIÓN — REQUIERE REMEDIACIÓN CRÍTICA. Se recomienda: rotar inmediatamente todos los secretos expuestos y eliminarlos del historial de git; implementar rate limiting/bloqueo de cuenta en login; cerrar los IDOR y validar cabeceras X-User-* con proxy de confianza; añadir sg-ms-gps al despliegue o quitar su referencia; corregir CORS y trusted IPs; y estandarizar paginación, manejo de errores y cobertura de tests.

Verificación E2E (entorno real): se verificó contra https://guardian-escolar.vercel.app (web) y https://school-guardian.duckdns.org (API/Kong). Resultado: login Admin ✅ (HTTP 200, JWT válido, permisos RBAC, rate limiting activo); login Superadmin ❌ (HTTP 401 INVALID_CREDENTIALS); profile ✅ (HTTP 200); endpoints de servicios .NET (schools, buses, routes, alerts) ❌ (HTTP 404 en todos).
